# PoC 生成AIナレッジ活用DB構築

社内ナレッジを対象とした RAG 検索基盤の設計・検証。
業務側では要件定義を担当し、技術検証は個人の Azure 環境で実装・評価した。

## 背景・課題

規制産業の設計文書レビュー業務では、チェックリストに沿って複数の基準（社内基準・顧客基準・法基準）と照合する必要があり、根拠資料の参照に工数がかかる。

- 参照すべき資料が複数形式（PDF・Office 文書）に分散している
- レビュー観点が文書化されておらず、担当者の経験に依存している
- 生成AIに投げるだけでは、根拠のない回答（ハルシネーション）が混ざる

「根拠を示せること」が要件の中心になるため、検索の精度と、判定をどこで行うかの設計が鍵になる。

## システム構成

```
利用者（チェックリストを添付してレビュー依頼）
    ↓
エージェント（Copilot Studio）
    ├─ Dataverse ………… ルールに基づく判定
    └─ Azure AI Search … 根拠となる記述の検索
    ↓
LLM（判定結果と根拠を文章化）
    ↓
回答
```

### 役割分担の設計判断

判定ロジックを LLM に任せず、**Dataverse 側の構造化ルールで行う**構成を選択した。

| 層 | 担当 | 理由 |
|---|---|---|
| Dataverse | 合否判定 | ルールが明示的で、結果が再現する |
| Azure AI Search | 根拠の検索 | 非構造の文書から該当箇所を引く |
| LLM | 文章化 | 判定者にはしない |

LLM を判定者にすると、同じ入力でも結果が揺れ、レビュー業務としての監査可能性が失われる。判定と生成を分離することで、出力の根拠を追跡できる形にした。

## 技術スタック

- **Azure AI Search** — インデックス作成、ベクトル検索、ハイブリッド検索、セマンティックランカー
- **Azure OpenAI** — `text-embedding-3-small`（1536次元）、`gpt-4.1-mini`、`gpt-5-mini`
- **Azure Document Intelligence** — 文書からのテキスト抽出
- **Azure Data Lake Storage Gen2** — 原本の格納
- **Dataverse** — ルール・メタデータの構造化管理
- **Copilot Studio** — エージェント層（BYOM 構成）
- **Python SDK / PowerShell** — 検証スクリプト

## 実装の工夫

### 1. チャンク分割とインデックス設計

非構造の文書をそのまま投入しても、検索単位が大きすぎて該当箇所を絞り込めない。

- Blob Storage と「データのインポートとベクター化」ウィザードを用いた自動チャンク分割を実施
- 埋め込み生成（テキスト → 1536次元ベクトル）は Python SDK で自前実装し、処理内容を把握したうえで組み込んだ
- メタデータの保持先を Dataverse 側と検索側のどちらにするか検討し、PoC 段階では検索側に一本化。後から構造化側へ付与できる順序を選んだ

### 2. 検索方式の比較

同一データに対して4方式をすべて実装し、結果を比較した。

| 方式 | 仕組み | 向き不向き |
|---|---|---|
| フルテキスト | BM25 | 語が一致すれば強い。言い換えに弱い |
| ベクトル | コサイン類似度 | 言い換えに強い。固有名詞で外すことがある |
| ハイブリッド | RRF で統合 | 両方の弱点を相互に補う |
| セマンティックランカー | 再ランキング | 上位の並び替えに効く |

実データでは、質問文が文書中の表記と一致するかどうかで検索スコアが明確に変動した。同義語の扱いが精度を左右するため、同義語マップの整備を次の課題として設定している。

### 3. 精度に効く変数の切り分け

「検索は正しいのに LLM がわからないと答える」事象に遭遇したため、原因を変数ごとに切り分けた。同一データ・同一検索結果で条件を変えて比較している。

| 条件 | 結果 |
|---|---|
| 厳格なプロンプト × 言い換え語で質問 | 回答不能 |
| 緩いプロンプト × 言い換え語で質問 | 回答するが、根拠にない補足が混入 |
| 厳格なプロンプト × 文書と一致する語で質問 | 過不足なく回答（検索スコアも上昇） |
| 厳格なプロンプト × 上位世代モデルに変更 | 過不足なく回答 |

あわせて temperature も検証したが、回答可否にも余計な補足にも影響しなかった。

**得られた整理**

- モデルの世代 … 言い換えを同一概念と判断できるか
- プロンプト … 答えるか、何を書くか
- temperature … 表現の揺れ幅のみ。判断や構成には効かない

プロンプトを緩めて回答させる対処は、根拠にない補足を生む副作用がある。検索側の精度かモデル側の理解力で解決すべき問題を、プロンプトの緩和で塞ぐべきではないという判断に至った。

## トラブルシュートの記録

実構築で踏んだ問題と解決内容。

- 特定リージョンでモデルのクォータが不足 → 利用可能なモデルへ切り替えて構成を成立させた
- 学習記事のエンドポイント形式が現行仕様と異なり 404 → 接続パラメータの指定方法を変更して解決
- ストレージの階層型名前空間へのアップグレードが論理削除設定で連続失敗 → 非対応設定を順に無効化して通過（非対応項目が1つずつしか表示されない仕様に留意）
- 認証がテナントのセキュリティ既定値で弾かれる → デバイスコードフローからクライアント資格情報フローへ変更し、アプリケーションユーザーを登録する構成にした

## 学習ポイント

- RAG は「検索」と「生成」の2段階であり、精度問題はどちらに起因するかを切り分けないと対処を誤る
- 判定を LLM に委ねない設計は、監査が求められる業務では必須の判断になる
- 検索方式は用途によって使い分けるもので、常にハイブリッドが最適とは限らない
- クラウドサービスは学習記事と現行仕様が乖離しやすく、公式ドキュメントと実機で確認する必要がある
